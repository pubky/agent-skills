# Core concepts to mobile methods

This file maps each Pubky protocol concept to the mobile methods that implement it. The theory behind each concept is in the `pubky` skill, linked from the left column of the table. Signatures, response shapes and platform setup are in [`react-native.md`](./react-native.md), [`native-ffi.md`](./native-ffi.md) and [`ring-auth.md`](./ring-auth.md).

## SDKs and conventions

| SDK | Pin | Wraps |
| :-- | :-- | :-- |
| React Native: [`@synonymdev/react-native-pubky`](https://www.npmjs.com/package/@synonymdev/react-native-pubky) | `0.15.0` | The FFI below. Its bundled bindings match FFI `cecd67c`. |
| UniFFI Swift/Kotlin: [`pubky-core-ffi`](https://github.com/pubky/pubky-core-ffi) (crate `pubkycore` 0.4.0) | Pin a commit SHA (`cecd67c` or later). The crate is not on crates.io and the repo has no tags. | `pubky` 0.16.1 |

- **Compare against the `pubky` 0.16 API.** The `pubky` skill references describe `pubky` 0.16.2, while the FFI wraps 0.16.1. Where they differ, check [docs.rs/pubky](https://docs.rs/pubky) for the version that the bindings wrap.
- **The RN setup scripts clone FFI `main`, not a pinned SHA.** If you rebuild the bindings from source, you get whatever `main` contains at that moment.
- **Method names match across bindings.** Rust FFI uses `snake_case` (`delete_file`). Swift, Kotlin and RN JS use `lowerCamelCase` (`deleteFile`), and that includes record fields (`sessionSecret`). Swift adds argument labels, for example `signUp(secretKey:homeserver:signupToken:clientId:)`. Fields inside JSON payloads stay `snake_case` (`grant_id`, `grant_secret`, `signup_token`).
- **Both SDKs have two error models:**
  - **Legacy functions.** FFI returns `[error, data]` strings, where `error` is the **string** `"true"` or `"false"` ([native-ffi.md → the `[error, data]` convention](./native-ffi.md#the-error-data-convention-legacy-family)). RN returns `Result<T>` with a string message.
  - **New 0.16 APIs.** These cover typed storage, events, locks, client config, blocking sign-in and the advanced grant flow. FFI returns a native `Result`, and Swift and Kotlin throw `PubkyCoreError`. RN returns `Result<T>`, and its error is a `PubkyError` with `kind`, `operation`, `status`, `retryable` and `expired`.
  - **RN never throws.** Check `isErr()` before you read `.value` ([react-native.md → The Result envelope](./react-native.md#result-and-errors)).
- **Every FFI call that does network I/O blocks the calling thread** (`block_on`), in legacy and new APIs alike. Keep FFI calls off the UI thread.
- **RN typed encodings:** binary values cross the bridge as padded base64 (`Base64Data`). `u64` values come back as decimal strings (`UInt64String`).
- **Key formats:**
  - Outputs are **bare z32** with no `pubky` prefix. `uri` fields use `pk:<z32>`.
  - Public-key *parameters* accept a bare or a prefixed key. Pass bare z32.
  - Keys inside URLs must be raw z32 (`pubky://<z32>/…`). `pubky` 0.16 rejects `pubky://pubky<z32>/…`.
  - See [native-ffi.md → String Contracts](./native-ffi.md#string-contracts) and [concepts.md → Public-key string formats](../../pubky/references/concepts.md#public-key-string-formats).
- **Android:** initialize rustls once, before any TLS call ([native-ffi.md → MANDATORY: Android rustls init](./native-ffi.md#mandatory-android-rustls-init)). RN does this for you (`RustlsInit.ensure` in `PubkyModule`). If you use the FFI directly, you must do it yourself, because the FFI repo's Android bindings ship no `RustlsInit` Kotlin object. iOS has no equivalent step.

## Concept-to-method map

The method names below are `lowerCamelCase` (RN, Swift, Kotlin).

| Concept (canonical theory) | Mobile method(s) | Gotcha |
| :-- | :-- | :-- |
| Ed25519 identity ([concepts.md](../../pubky/references/concepts.md#identity-the-ed25519-keypair)) | `generateSecretKey`, `getPublicKeyFromSecretKey`, `generateMnemonicPhrase`, `mnemonicPhraseToKeypair`, `generateMnemonicPhraseAndKeypair`, `validateMnemonicPhrase` | Use these only in authenticator-type apps. A third-party app must never ask for a mnemonic or a secret key. Use Ring instead ([concepts.md → Authentication](../../pubky/references/concepts.md#authentication)). |
| Recovery files ([concepts.md](../../pubky/references/concepts.md#identity-the-ed25519-keypair)) | `createRecoveryFile(secretKey, passphrase)`, `decryptRecoveryFile(recoveryFile, passphrase)` | These only create and decrypt a local Base64 backup. Both reject empty inputs. Backup *restore* and cloud backup are planned, not shipped ([shipped-vs-planned.md](../../pubky/references/shipped-vs-planned.md#backup-restore-and-mirroring)). |
| `pubkyauth`, **requesting app** ([auth.md](../../pubky/references/auth.md#grant-auth-model), [capabilities](../../pubky/references/auth.md#capabilities), [sign-up via flow](../../pubky/references/auth.md#sign-up-through-the-flow)) | Simple: `startAuthFlow(capabilities, clientId)` returns a `pubkyauth://` URL. `awaitAuthApproval()` then returns grant session JSON (`pubky`, `grant_id`, `grant_secret`, expiries, …). Configurable: `startGrantAuthFlowWithConfig(config)` returns a flow state (`authorizationUrl`, `clientKeySecret`, optional `approvalKeySecret`). Set `homeserver` for a signup flow and leave it unset for a signin flow. | Third-party apps should use this path. **A process holds only one pending grant flow.** Any grant-flow start or restore overwrites it. An await consumes the flow even when it fails, so a second await without a new start returns an error. Store the configurable start result in Keychain/Keystore, because it holds secret keys. See [ring-auth.md](./ring-auth.md#two-roles-pick-the-right-one). |
| Resumable flows ([auth.md](../../pubky/references/auth.md#resume-after-reload-or-restart)) | `saveGrantAuthFlow`, `restoreGrantAuthFlow(state)`, `pollGrantAuthFlow()` (one non-blocking probe), `awaitGrantAuthFlow()`, `cancelGrantAuthFlow()` | You can save and cancel a flow **only while you poll it**. Once `awaitGrantAuthFlow` is waiting, the flow can't be saved and `cancelGrantAuthFlow` won't abort it. The saved state holds secret keys (`clientKeySecret`, optional `approvalKeySecret`), so keep it in Keychain/Keystore. |
| `pubkyauth`, **authenticator / Ring** ([auth.md](../../pubky/references/auth.md#authenticator-side-approving-requests)) | `auth(url, secretKey)` approves everything the request asks for. `authWithCapabilities(url, secretKey, approved)` approves a comma-separated `scope:actions` subset, and `""` approves nothing. `parseAuthUrl(url)` returns `kind` (`signin`, `signup`, `signin_grant` or `signup_grant`). For signup kinds, it also returns `homeserver` and `signup_token`. `parseDeepLink(url)` | This is Ring's job, so your app rarely needs these methods ([ring-auth.md → Deeplink schemes](./ring-auth.md#deeplink-schemes-and-intents)). 0.16 grant requests produce the `*_grant` kinds. The SDK rejects an approval that grants more than the request asked for. |
| Homeserver signup/signin ([concepts.md](../../pubky/references/concepts.md#the-homeserver-model), [auth.md → pick the right path](../../pubky/references/auth.md#pick-the-right-path)) | `signUp(secretKey, homeserver, signupToken, clientId)`, `signIn(secretKey, clientId)`, which are aliases of `signUpGrant` and `signInGrant`. `signInGrantBlocking` (typed) | Key-based sign-in grants **root `/:rw`**, so use it only in authenticator and first-party apps. `homeserver` is the homeserver's **public key**: pass it as bare z32. `clientId` is required. In Swift, `signupToken: String?` has no default, so pass `nil` explicitly. |
| Session lifecycle ([auth.md](../../pubky/references/auth.md#session-lifecycle), [persisting](../../pubky/references/auth.md#persist-and-restore)) | `revalidateSession(sessionSecret)`, `signOut(sessionSecret)` | Both accept a grant's `grant_secret` or a legacy cookie `session_secret`. These are bearer secrets: store them in Keychain/Keystore and never log them ([ring-auth.md](./ring-auth.md#store-and-revoke-the-grant_secret)). |
| Grant management ([auth.md](../../pubky/references/auth.md#list-and-revoke-grants)) | `listGrants(sessionSecret)`, `revokeGrant(sessionSecret, grantId)` | These need a session with root capability. Revoking a grant kills every session minted from it. Leave your own `grant_id` out of any revocable list you show the user, or the user can revoke your management session. |
| Legacy cookie auth ([auth.md → deprecated](../../pubky/references/auth.md#deprecated-cookie-auth)) | `signUpCookie`, `signInCookie`, `signInCookieBlocking` (typed), `startCookieAuthFlow`, `awaitCookieAuthApproval` | These are deprecated upstream. Don't use them in new code ([native-ffi.md](./native-ffi.md#auth-strategies-and-session-secrets)). The cookie flow has its own pending slot, separate from the grant flow's. |
| Signup tokens ([auth.md](../../pubky/references/auth.md#signup-tokens)) | `getSignupToken(homeserverPubky, adminPassword)` | **Don't rely on this method.** It calls `https://<pubky>/admin/generate_signup_token`, but the homeserver serves `/generate_signup_token` on its separate admin listener. It also ignores the HTTP status. It is for operators and admins only, so never ship the admin password in an end-user app. For the operator side, see [signup-gating.md](../../pubky-infra/references/signup-gating.md). |
| Write **own** data ([concepts.md](../../pubky/references/concepts.md#own-data-vs-another-users-data), [storage roots](../../pubky/references/concepts.md#storage-roots-and-access)) | Typed (prefer these): `sessionPutBytes(pathOrAddress, content, sessionSecret)`, `sessionDelete`, `sessionGetBytes`, `sessionExists`, `sessionStats`, `sessionList`. Legacy: `putWithSession(url, content, sessionSecret)` and `deleteWithSession`. Legacy key-based: `put(url, content, secretKey, clientId)` and `deleteFile`. | Typed calls take a `/pub/…` path, a `/priv/…` path ([alpha, see below](../../pubky/references/shipped-vs-planned.md#priv-private-storage-alpha)) or an address. They **reject** an address that another key owns. Legacy calls write only the URL's `/pub/…` path, and *always to your own storage*, even if the URL names someone else's key. Key-based calls sign in again on every call. The method is `deleteFile`, **not** `delete`. RN `put` and `putWithSession` encode content differently ([react-native.md](./react-native.md#data-operations)). |
| `/priv` private storage ([shipped-vs-planned.md](../../pubky/references/shipped-vs-planned.md#priv-private-storage-alpha)) | Typed `session*` storage calls with a `/priv/…` path | **Alpha. Don't use it in production.** Access is controlled, but the data is **not encrypted from the homeserver operator**, and no backup tool exists. This reference hasn't verified it against a homeserver. |
| Public read of **anyone's** data ([concepts.md](../../pubky/references/concepts.md#own-data-vs-another-users-data)) | Typed: `publicGetBytes`, `publicExists`, `publicStats`, `publicList(address, options)`. Legacy: `get(url)`, `list(url)` | None of these calls authenticate. Legacy `get` returns text, or `base64:<…>` for bytes that aren't UTF-8. Listings return `pubky://` URLs with raw-z32 keys. |
| Homeserver event streams ([concepts.md](../../pubky/references/concepts.md#homeserver-write-vs-nexus-read)) | `startEventStream(config, listener)`, `stopEventStream(id)`, `stopAllEventStreams()` | `config.users` needs at least one entry. Streaming `/priv` paths needs `sessionSecret`, and `/priv` is [alpha, not for production and not encrypted from the operator](../../pubky/references/shipped-vs-planned.md#priv-private-storage-alpha). Each event has an `eventType` (`PUT` or `DEL`), a `resource`, a `cursor` and a `contentHash`. **`setEventListener`/`removeEventListener` are still a placeholder timer**, not a stream ([native-ffi.md](./native-ffi.md#event-streams-typed)). |
| WebDAV locks | RN: `acquireStorageLock`, `refreshStorageLock`, `putWithStorageLock`, `deleteWithStorageLock`, `releaseStorageLock`. FFI: a `sessionLock(…)` handle with `unlock()` | RN `releaseStorageLock` drops the local handle even when the server-side unlock fails. The server then keeps the lock until it times out. FFI `unlock()` returns the error before it clears the handle, so Swift and Kotlin callers can retry. |
| PKARR / discovery ([concepts.md](../../pubky/references/concepts.md#pkarr-resolution)) | `resolve`, `resolveHttps`, `getHomeserver(pubky)`, `republishHomeserver(secretKey, homeserver)`, `publish` (TXT), `publishHttps` (HTTPS/SVCB) | `getHomeserver` returns a bare z32 key, not a URL. **`publish` and `publishHttps` replace the whole signed packet.** Under a user's identity key, that wipes the `_pubky` homeserver record ([native-ffi.md](./native-ffi.md#pkarr--dns-vector)). |
| Testnet vs mainnet, client tuning | `switchNetwork(useTestnet)`, `configureClient(config)` (RN and FFI) | Each call rebuilds the **process-wide** client. The change applies only to sessions and requests created after it. A `configureClient` call without `useTestnet` or `testnetHost` switches back to mainnet, so a call that only sets timeouts silently undoes `switchNetwork(true)`. |
| Scoped encryption keys, signed approvals, custom proofs (`pubky` 0.16) ([app-side crypto](../../pubky/references/shipped-vs-planned.md#app-side-ciphertext-is-your-own-crypto)) | `approvalFormat: 'signedApprovalV1'`, `deriveGrantEncryptionKey(sessionSecret, path)`, `grantEncryptionKeyScopes`, `createCustomGrantProof`, `verifyCustomGrantProof` | These give your app **key material, not encrypted storage**. The keys are permanent: revoking the grant or letting it expire doesn't take them back, and they can't be rotated. A key for a directory covers everything below it. Requesting keys requires signed approvals and upgraded homeservers and signers ([upstream doc](https://github.com/pubky/pubky-homeserver/blob/main/docs/scoped-encryption-keys.md)). |

## Not on the mobile surface

- **No Nexus client.** Call Nexus `/v0` over plain HTTP ([nexus-api.md](../../pubky/references/nexus-api.md)). `/v0` is unstable and prone to breaking changes.
- **No pubky-app-specs binding,** and no generic JSON get or put. Build and validate the JSON yourself following [app-specs.md](../../pubky/references/app-specs.md#models), then write the bytes. The specs are v0.x, the `/pub` layout is not stabilized, and `PubkyId` must be [raw z32](../../pubky/references/app-specs.md#pubkyid-raw-z32-only).
