# Core concepts to mobile methods

This file maps each Pubky protocol concept to the mobile methods that implement it. The theory behind each concept is in the `pubky` skill, linked from the left column of the table. Signatures, response shapes and platform setup are in [`react-native.md`](./react-native.md), [`native-ffi.md`](./native-ffi.md) and [`ring-auth.md`](./ring-auth.md).

## SDKs and conventions

| SDK | Pin | Wraps |
| :-- | :-- | :-- |
| React Native: [`@synonymdev/react-native-pubky`](https://www.npmjs.com/package/@synonymdev/react-native-pubky) | `0.15.0` | The FFI below. Its bundled bindings are byte-identical to FFI `cecd67c`. |
| UniFFI Swift/Kotlin: [`pubky-core-ffi`](https://github.com/pubky/pubky-core-ffi) (crate `pubkycore` 0.4.0) | Pin a commit SHA (`cecd67c` or later). The crate is not on crates.io and the repo has no tags. | `pubky` 0.16.1 |

- **Mobile is behind the `pubky` SDK.** The FFI wraps `pubky` 0.16.1, while crates.io is at 0.18.0 (0.17.1 shipped 2026-10-26). Anything the `pubky` skill documents from 0.17 or later, or from unreleased `main`, is **not** on mobile. Examples: the account API (`session.grant.account()` in JS, `GrantSessionView::account()` in Rust), expected-identity grant links and `TlsVerification` errors (0.18.0), and child grants (unreleased `main`, not in 0.18.0). When the docs differ, check [docs.rs/pubky/0.16.1](https://docs.rs/pubky/0.16.1/pubky/).
- **The RN setup scripts clone FFI `main`, not a pinned SHA.** If you rebuild the bindings from source, you get whatever `main` contains at that moment.
- **Method names match across bindings.** Rust FFI uses `snake_case` (`delete_file`). Swift, Kotlin and RN JS use `lowerCamelCase` (`deleteFile`), and that includes record fields (`sessionSecret`). Swift adds argument labels, for example `signUp(secretKey:homeserver:signupToken:clientId:)`. Fields inside JSON payloads stay `snake_case` (`grant_id`, `grant_secret`, `signup_token`).
- **Both SDKs have two error models:**
  - **Legacy functions.** FFI returns `[error, data]` strings, where `error` is the **string** `"true"` or `"false"` ([native-ffi.md → the `[error, data]` convention](./native-ffi.md#the-error-data-convention-legacy-family)). RN returns `Result<T>` with a plain string message.
  - **Typed 0.16 APIs.** These cover typed storage, events, locks, client config, blocking sign-in and the configurable grant flow. FFI returns `Result<_, PubkyCoreError>`, and Swift and Kotlin throw it. Its variants are `Transport`, `Server{status}`, `Validation`, `DecodeJson`, `Pkarr{retryable}`, `Parse`, `Authentication{expired}`, `Build` and `State`. RN returns `Result<T>` whose error is a `PubkyError` with `kind`, `operation`, `status`, `retryable`, `expired` and `nativeCode`.
  - **RN never throws.** Check `isErr()` before you read `.value` ([react-native.md → Result and errors](./react-native.md#result-and-errors)).
- **Threading.** Every FFI call that does network I/O blocks the calling thread (`block_on`), in legacy and typed APIs alike. Keep FFI calls off the UI thread ([native-ffi.md → Never call on the main/UI thread](./native-ffi.md#never-call-on-the-mainui-thread)):
  - `pollGrantAuthFlow` counts too: once an approval has arrived, it does a blocking credential exchange with the homeserver.
  - Grant-flow start and restore return at once, but they start relay polling in the background, so they are not free of network I/O.
  - These make no network calls: flow save and cancel, `stopEventStream` and `stopAllEventStreams`, and the local key, mnemonic, recovery-file, link-parsing, custom-proof and grant-key calls (marked "local" in the table).
- **RN typed encodings:** binary values cross the bridge as padded base64 (`Base64Data`). `u64` values come back as decimal strings (`UInt64String`).
- **Key formats:**
  - Outputs are **bare z32** with no `pubky` prefix. `uri` fields use `pk:<z32>`.
  - Public-key *parameters* accept a bare or a prefixed key. Pass bare z32.
  - Keys inside URLs must be raw z32 (`pubky://<z32>/…`). The storage URL parser rejects `pubky://pubky<z32>/…`.
  - See [native-ffi.md → String Contracts](./native-ffi.md#string-contracts) and [concepts.md → Public-key string formats](../../pubky/references/concepts.md#public-key-string-formats).
- **Android:** initialize rustls once, before any TLS call, or pkarr relay TLS panics with `Expect rustls-platform-verifier to be initialized` ([native-ffi.md → MANDATORY: Android rustls init](./native-ffi.md#mandatory-android-rustls-init)). RN does this for you (`RustlsInit.ensure` in `PubkyModule`). If you use the FFI directly, you must do it yourself, because the FFI repo's Android bindings ship no `RustlsInit` Kotlin object. iOS has no equivalent step.

## Concept-to-method map

The method names below are `lowerCamelCase` (RN, Swift, Kotlin).

| Concept (canonical theory) | Mobile method(s) | Gotcha |
| :-- | :-- | :-- |
| Ed25519 identity ([concepts.md](../../pubky/references/concepts.md#identity-the-ed25519-keypair)) | `generateSecretKey`, `getPublicKeyFromSecretKey`, `generateMnemonicPhrase`, `mnemonicPhraseToKeypair`, `generateMnemonicPhraseAndKeypair`, `validateMnemonicPhrase` | Local. Use these only in authenticator-type apps. A third-party app must never ask for a mnemonic or a secret key. Use Ring instead ([concepts.md → Authentication](../../pubky/references/concepts.md#authentication)). |
| Recovery files ([concepts.md](../../pubky/references/concepts.md#identity-the-ed25519-keypair)) | `createRecoveryFile(secretKey, passphrase)`, `decryptRecoveryFile(recoveryFile, passphrase)` | Local. These only create and decrypt a local base64 backup, and both reject empty inputs. Backup *restore* and cloud backup are planned, not shipped ([shipped-vs-planned.md](../../pubky/references/shipped-vs-planned.md#backup-restore-and-mirroring)). |
| `pubkyauth`, **requesting app** ([auth.md](../../pubky/references/auth.md#grant-auth-model), [capabilities](../../pubky/references/auth.md#capabilities), [sign-up via flow](../../pubky/references/auth.md#sign-up-through-the-flow), [approval format](../../pubky/references/auth.md#approval-format-bare-grant-or-signed-approval)) | Simple (always signin): `startAuthFlow(capabilities, clientId)` returns a `pubkyauth://` URL. `awaitAuthApproval()` then returns grant session JSON (`pubky`, `grant_id`, `grant_secret`, expiries, …). These alias `startGrantAuthFlow` and `awaitGrantAuthApproval`. Configurable: `startGrantAuthFlowWithConfig(config)` returns a flow state (`authorizationUrl`, `clientKeySecret`, optional `approvalKeySecret`). Set `homeserver` for a signup flow and leave it unset for a signin flow. `approvalFormat` is `'bareGrant'` or `'signedApprovalV1'`. | Third-party apps should use this path. **A process holds only one pending grant flow.** Any grant-flow start or restore overwrites it. An await consumes the flow even when it fails, so a second await without a new start returns `No … auth flow in progress`. Store the configurable start result in Keychain/Keystore, because it holds secret keys. See [ring-auth.md](./ring-auth.md#two-roles-pick-the-right-one). |
| Resumable flows ([auth.md](../../pubky/references/auth.md#resume-after-reload-or-restart)) | `saveGrantAuthFlow`, `restoreGrantAuthFlow(state)`, `pollGrantAuthFlow()` (one non-blocking relay probe, returns session or `null`), `awaitGrantAuthFlow()`, `cancelGrantAuthFlow()` | Save or cancel a flow **only while it is idle in the slot**: after start or restore, and between poll calls. A poll takes the flow out of the slot and puts it back on `null` or an error, so during an in-flight poll a save errors with `No Grant auth flow is in progress`, and a cancel, start or restore is silently undone or overwritten when the poll returns. Serialize these calls. Once `awaitGrantAuthFlow` is waiting, the flow can't be saved and `cancelGrantAuthFlow` won't abort it. The saved state holds secret keys (`clientKeySecret`, optional `approvalKeySecret`), so keep it in Keychain/Keystore. |
| `pubkyauth`, **authenticator / Ring** ([auth.md](../../pubky/references/auth.md#authenticator-side-approving-requests), [selective approval](../../pubky/references/auth.md#selective-approval)) | `auth(url, secretKey)` approves everything the request asks for. `authWithCapabilities(url, secretKey, approved)` approves a comma-separated `scope:actions` subset, and `""` approves nothing. `parseAuthUrl(url)` (local) returns `kind` (`signin`, `signup`, `signin_grant` or `signup_grant`), plus `homeserver` and `signup_token` for signup kinds and `approval_format` for grant kinds. `parseDeepLink(url)` (local) | This is Ring's job, so your app rarely needs these methods ([ring-auth.md → Deeplink schemes](./ring-auth.md#deeplink-schemes-and-intents)). 0.16 grant requests produce the `*_grant` kinds; the FFI README's claim of only `signin`/`signup` is stale. The SDK rejects an approval that grants more than the request asked for. |
| Homeserver signup/signin ([concepts.md](../../pubky/references/concepts.md#the-homeserver-model), [auth.md → pick the right path](../../pubky/references/auth.md#pick-the-right-path)) | `signUp(secretKey, homeserver, signupToken, clientId)`, `signIn(secretKey, clientId)`, which are aliases of `signUpGrant` and `signInGrant`. `signInGrantBlocking` (typed) | Key-based sign-in grants **root `/:rw`**, so use it only in authenticator and first-party apps. `homeserver` is the homeserver's **public key**: pass it as bare z32. `clientId` is required. In Swift, `signupToken: String?` has no default, so pass `nil` explicitly. RN maps `""` to no token. |
| Session lifecycle ([auth.md](../../pubky/references/auth.md#session-lifecycle), [persisting](../../pubky/references/auth.md#persist-and-restore)) | `revalidateSession(sessionSecret)`, `signOut(sessionSecret)` | Both accept a grant's `grant_secret` or a legacy cookie `session_secret`. `revalidateSession` errors when the session is expired or invalidated. These are bearer secrets: store them in Keychain/Keystore and never log them ([ring-auth.md](./ring-auth.md#store-and-revoke-the-grant_secret)). |
| Grant management ([auth.md](../../pubky/references/auth.md#list-and-revoke-grants)) | `listGrants(sessionSecret)`, `revokeGrant(sessionSecret, grantId)` | These need a session with root capability. Revoking a grant kills every session minted from it. Leave your own `grant_id` out of any revocable list you show the user, or the user can revoke your management session. |
| Legacy cookie auth ([auth.md → deprecated](../../pubky/references/auth.md#deprecated-cookie-auth)) | `signUpCookie`, `signInCookie`, `signInCookieBlocking` (typed), `startCookieAuthFlow`, `awaitCookieAuthApproval` | Deprecated upstream. Don't use them in new code ([native-ffi.md](./native-ffi.md#auth-strategies-and-session-secrets)). The cookie flow has its own pending slot, separate from the grant flow's. |
| Signup tokens ([auth.md](../../pubky/references/auth.md#signup-tokens)) | `getSignupToken(homeserverPubky, adminPassword)` | **Don't rely on this method.** It calls `https://<pubky>/admin/generate_signup_token`, but the homeserver serves `/generate_signup_token` on its separate admin listener. It also ignores the HTTP status. It is for operators only, so never ship the admin password in an end-user app. For the operator side, see [signup-gating.md](../../pubky-infra/references/signup-gating.md). |
| Write **own** data ([concepts.md](../../pubky/references/concepts.md#own-data-vs-another-users-data), [storage roots](../../pubky/references/concepts.md#storage-roots-and-access)) | Typed (prefer these): `sessionPutBytes(pathOrAddress, content, sessionSecret)`, `sessionDelete`, `sessionGetBytes`, `sessionExists`, `sessionStats`, `sessionList`. Legacy: `putWithSession(url, content, sessionSecret)` and `deleteWithSession`. Legacy key-based: `put(url, content, secretKey, clientId)` and `deleteFile`. | Typed calls take an absolute path or an address, and **reject** an address that another key owns. Legacy calls need `/pub/` in the URL, write only from `/pub/…` onward, and *always to your own storage*, even if the URL names someone else's key. Key-based calls sign in again on every call. The method is `deleteFile`, **not** `delete`. RN `put` `JSON.stringify`s its content; `putWithSession` sends the string as-is ([react-native.md](./react-native.md#data-operations)). |
| `/priv` private storage ([shipped-vs-planned.md](../../pubky/references/shipped-vs-planned.md#priv-private-storage-alpha)) | Typed `session*` storage, event and lock calls with a `/priv/…` path | **Alpha. Don't use it in production.** Access is controlled, but the data is **not encrypted from the homeserver operator**, and no backup tool exists. The calls merely accept the path (code presence); this reference hasn't verified it against a homeserver. The upstream RN example requests `/priv` capabilities; don't copy that into production code. |
| Public read of **anyone's** data ([concepts.md](../../pubky/references/concepts.md#own-data-vs-another-users-data)) | Typed: `publicGetBytes`, `publicExists`, `publicStats`, `publicList(address, {reverse, shallow, limit, cursor})`. Legacy: `get(url)`, `list(url)` | None of these calls authenticate. Legacy `get` returns text, or `base64:<…>` for bytes that aren't UTF-8. Listings return `pubky://` URLs with raw-z32 keys. Typed `nextCursor` is the last entry's URL. |
| Homeserver event streams ([concepts.md](../../pubky/references/concepts.md#homeserver-write-vs-nexus-read)) | `startEventStream(config, listener)` (RN returns `{id, remove()}`), `stopEventStream(id)`, `stopAllEventStreams()` | `config.users` needs at least one entry. Streaming `/priv` paths needs `sessionSecret`, and `/priv` is [alpha, not for production and not encrypted from the operator](../../pubky/references/shipped-vs-planned.md#priv-private-storage-alpha). Each event has an `eventType` (`PUT` or `DEL`), a `resource`, a `cursor` and a `contentHash`. **`setEventListener`/`removeEventListener` are a placeholder 2-second timer**, not a stream ([native-ffi.md](./native-ffi.md#event-streams-typed)). |
| WebDAV locks ([concepts.md](../../pubky/references/concepts.md#storage-locks)) | RN: `acquireStorageLock`, `refreshStorageLock`, `putWithStorageLock`, `deleteWithStorageLock`, `releaseStorageLock`. FFI: a `sessionLock(…)` handle with `info`/`refresh`/`put`/`delete`/`unlock` | RN `releaseStorageLock` (iOS and Android) drops the local handle even when the server-side unlock fails. The server then keeps the lock until it times out. FFI `unlock()` returns the error before it clears the handle, so Swift and Kotlin callers can retry. |
| PKARR / discovery ([concepts.md](../../pubky/references/concepts.md#pkarr-resolution)) | `resolve`, `resolveHttps`, `getHomeserver(pubky)`, `republishHomeserver(secretKey, homeserver)`, `publish` (TXT), `publishHttps` (HTTPS/SVCB) | `getHomeserver` returns a bare z32 key, not a URL. **`publish` and `publishHttps` replace the whole signed packet.** Under a user's identity key, that wipes the `_pubky` homeserver record ([native-ffi.md](./native-ffi.md#pkarr--dns-vector)). |
| Testnet vs mainnet, client tuning | `switchNetwork(useTestnet)`, `configureClient(config)` (RN and FFI) | Each call rebuilds the **process-wide** client from scratch, so every `configureClient` call must restate the network. The change applies only to sessions and requests created after it. `testnetHost` wins over `useTestnet`. In RN, omitting `useTestnet`/`testnetHost` selects mainnet, so a call that only sets timeouts silently undoes `switchNetwork(true)`. In Swift and Kotlin, `useTestnet` is a required field. |
| Scoped encryption keys, signed approvals ([auth.md](../../pubky/references/auth.md#scoped-encryption-keys), [app-side crypto](../../pubky/references/shipped-vs-planned.md#app-side-ciphertext-is-your-own-crypto)) | `approvalFormat: 'signedApprovalV1'`, `deriveGrantEncryptionKey(sessionSecret, path)` (32-byte base64 or `null`), `grantEncryptionKeyScopes` (`null` = bare grant, `[]` = signed approval with no keys), `grantSignedApproval(sessionSecret)` (the confidential signed approval, or `null`). All three are local. | These give your app **key material, not encrypted storage**. The keys are permanent: revoking the grant or letting it expire doesn't take them back, and they can't be rotated. A key for a directory covers everything below it. Treat the signed approval and derived keys as secrets. Requesting keys requires signed approvals and upgraded homeservers and signers ([upstream doc](https://github.com/pubky/pubky-homeserver/blob/main/docs/scoped-encryption-keys.md)). |
| Custom grant proofs ([auth.md](../../pubky/references/auth.md#custom-grant-proofs)) | `createCustomGrantProof(sessionSecret, data)` returns `{grant, proof}`. `verifyCustomGrantProof(proof, clockSkewSeconds)`: the default of `30` is RN-only, so Swift (`verifyCustomGrantProof(proof:clockSkewSeconds:)`) and Kotlin callers must pass it. | Local: neither calls the homeserver. Verification is offline, so your app still owns freshness and replay checks. |

## Not on the mobile surface

- **Anything from `pubky` 0.17 or later, or unreleased `main`** (see the first convention above).
- **No Nexus client.** Call Nexus `/v0` over plain HTTP ([nexus-api.md](../../pubky/references/nexus-api.md)). `/v0` is unstable and prone to breaking changes.
- **No pubky-app-specs binding,** and no generic JSON get or put: mobile callers encode and decode their own bytes. Build and validate the JSON yourself following [app-specs.md](../../pubky/references/app-specs.md#models), then write the bytes. The specs are v0.x, the `/pub` layout is not stabilized, and `PubkyId` must be [raw z32](../../pubky/references/app-specs.md#pubkyid-raw-z32-only).
- **Intentionally internal** per [`BINDING_PARITY.md`](https://github.com/pubky/pubky-core-ffi/blob/cecd67c161ba9d2a9ada1a131a2df9279fde882a/BINDING_PARITY.md): `RequestBuilder`, PKARR builder closures, raw relay channel actors, delegated browser PoP callbacks, and filesystem-path session/recovery helpers.

The FFI README `signUp` wrappers omit `clientId`, so they don't match the generated 4-argument signature, and its String Contracts list only `signin`/`signup` for `parseAuthUrl`.
